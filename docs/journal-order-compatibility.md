# 매매일지 입력 순서와 구버전 호환

- 거래일의 연·월·일을 우선한다. 같은 날은 최초 입력 시각 `createdAt` 순서로 계산한다. 숨겨진 거래 시각은 같은 날 정렬에 쓰지 않는다. 카드/차트 목록도 공통 비교 함수를 사용한다.
- 기존 기록을 재저장하지 않는다. 수정 시 `createdAt`은 유지하며 동시 변경 검사에도 포함한다. 입력 시각까지 같은 기록은 ID 정렬을 입력 순서로 간주하지 않고 확인 대상으로 둔다. 보유량 초과 검증도 유지한다.
- `createdAt`이 없는 레거시 문서는 저장된 거래일시로 대체한다. 둘 다 없으면 고정 epoch를 사용한다. 읽을 때마다 현재 시각을 생성해 순서가 바뀌는 것을 방지한다. 누락된 실제 입력 순서는 복원할 수 없다.
- 구버전의 trading_journal 추가·수정·삭제를 revision 문서 유무와 무관하게 허용하도록 로컬 규칙을 변경했다. 소유권 검사는 유지한다. 새 규칙은 운영에 배포하지 않았다.
- 신버전은 revision 문서 읽기만 permission-denied일 때 기존 권한으로 거래 검증/트랜잭션을 진행한다. 네트워크 오류나 실제 거래 쓰기 권한 오류를 성공으로 처리하지 않는다. 규칙을 배포하지 않은 기존 운영 환경에서도 저장을 시도할 수 있다. SDK 권한 경고 로그 자체는 남을 수 있다.
- 호환 모드에서도 기존 문서의 동시 수정/삭제는 트랜잭션으로 검사한다. 그러나 revision을 갱신하지 않는 구버전의 동시 신규 거래는 완전히 감지할 수 없다. 따라서 혼합 버전 또는 기존 규칙 환경에서 동시 전량 매도 안전성을 완전히 보장하지 않는다. 이를 보장하려면 서버에서 모든 거래를 일괄 조정하는 별도 설계가 필요하다.
- 이미 설치된 구버전 앱의 계산 코드는 원격으로 바뀌지 않는다. 이번 수정은 그 데이터/저장 방식과의 호환성을 유지하면서 신버전 계산을 개선한다.

## 검증

Flutter 회귀 테스트 27개, Firestore 에뮬레이터 테스트 4개. 같은 날 입력순 매수/매도, 숨겨진 시각, 과거 수정과 수량 초과, 기존 규칙 접근 거부 분기, 구버전 CRUD, 신버전 간 revision 충돌을 검사했다. 실제 운영 DB에는 쓰지 않았다.

## 롤백

`python tools/rollback_journal_order.py`로 검사하고 `--apply`로 이번 소스 변경을 복원한다. 백업 및 체크섬은 `output/journal-order-backup/20260913`에 있다. 이후 수정이 있으면 덮어쓰기를 거부하며 DB에는 접근하지 않는다. 복원한 규칙을 운영에 적용하려면 별도 배포가 필요하다.
